# ADR-001: Каноническая модель хранения сущности Project на базе PostgreSQL и изолированных Git-репозиториев

- **Статус:** Proposed (v2 — обновлено по итогам архитектурного ревью PR #7)
- **Дата:** 2026-10-15
- **Контекст:** Эпик 2.5 (пакет v3), спецификация хранения 2.3, контракт событий `events v0` (PR #8, направление 2.1), архитектура раннера 2.4
- **Целевой артефакт:** `docs/adr/ADR-001-storage.md`

---

## 1. Контекст и проблематика

В рамках разработки веб-направления CoreTeam необходимо формализовать каноническую схему хранения сущности `Project` и связанных с ней подсущностей (`materials`, `runs`, `events`, `artifacts`, `ctf_files`, `operations`), обеспечив согласованность между API/Gateway (2.1), хранилищем (2.3), раннером (2.4) и требованиями безопасности (2.5).

Согласно установочным требованиям заказчика (протокол установочной встречи с заказчиком / ТЗ v1, зафиксировано для контрольной точки 7.10; см. п. 5 «Открытые вопросы заказчику» для уточнения реквизитов протокола и лимитов), для версионируемого хранения сгенерированных отчетов (`text/markdown`), текстовых материалов и служебных манифестов в первой версии (v1) вместо облачного S3-хранилища используется **Git-репозиторий**.

### Требования и ограничения:
1. **Модель «Один Git-репозиторий на проект» (Repo-per-Project):** Каждый проект изолируется в собственном Git-репозитории (отдельный Git-том/репозиторий на стороне раннера 2.4). Использование единого монорепозитория на все проекты запрещено по требованиям изоляции тенантов (критерий 8 спеки 2.3 и гипотеза безопасности HADI-T3).
2. **Версионирование коммитами и трейлеры раннера:** Каждая подтвержденная версия артефакта и шага раннера фиксируется уникальным `commit_sha` (раннер 2.4 формирует коммит на каждый ход с трейлером `Turn-Id` и ключом операции `Operation-Id`).
3. **Ограничения на входные материалы (`materials`):** Git не предназначен для хранения тяжелых бинарных файлов. В Git коммитятся только текстовые и легковесные спецификации со строгим квотированием размера (`<= 5 МБ` на файл, `<= 25 МБ` суммарно на репозиторий проекта). Тяжелые бинарные файлы и датасеты не помещаются в Git-историю без выделенного контура (локальный том с передачей по `content_sha256` или Git LFS).
4. **Разделение контуров:** Внутренние рассуждения моделей, промежуточные токены и секреты не попадают в Git и не транслируются в публичные события.
5. **Идемпотентная двухфазная запись (`намерение -> коммит -> подтверждение`):** Переход в статус `completed` выставляется только после записи намерения (`operation_id`, `content_sha256`), физического `git commit` и фиксации публичного события `artifact.saved`.
6. **Единый словарь статусов и событий:** Названия статусов запуска (`runs.status`) и типов событий (`events.type`) строго синхронизированы со спецификацией 2.5 и контрактом `events v0` (PR #8).

## 2. Архитектурное решение (Decision)

Принята гибридная схема **PostgreSQL + изолированный Git-репозиторий на каждый проект (`repo-per-project`)**:
- **PostgreSQL:** хранит профили пользователей (`users`), метаданные проектов (`projects`), реестр входных материалов (`materials`), состояние запусков (`runs`), журнал идемпотентных операций записи (`operations`), строгий упорядоченный журнал публичных событий (`events`), метаданные артефактов (`artifacts`) и служебных файлов (`ctf_files`).
- **Git-репозиторий проекта (`project-repo-{project_id}.git`):** выступает изолированным версионированным хранилищем текстовых материалов, служебных манифестов (`.ctf/`) и итоговых отчетов (`runs/{run_id}/`).

### 2.1. Структура каталогов внутри Git-репозитория проекта

Каждый проект располагается в **отдельном Git-репозитории** (`projects.git_repo_url`), который монтируется только в контейнер раннера, обслуживающего данный `project_id`. Внутри репозитория проекта используется следующая раскладка:

```text
project-repo-root/ # Корень изолированного репозитория конкретного проекта
├── materials/ # Текстовые и легковесные входные материалы (лимит <= 5 МБ)
│ ├── business_requirements.md
│ └── api_contract.yaml
├── .ctf/ # Служебные файлы фреймворка (манифесты, роли, стейт)
│ ├── team_manifest.json
│ └── framework_state.json
└── runs/
    └── {run_id}/
        └── result.md # Итоговый подтвержденный артефакт запуска
```

*Примечание по бинарным файлам и лимитам (спека 2.3):* Загрузка файлов свыше 5 МБ или нетекстовых датасетов напрямую в Git блокируется на уровне Gateway. Если пользователю необходимо приложить PDF или датасет до 10–20 МБ, на этапе загрузки вычисляется `content_sha256`, извлекается текстовое представление (markdown extract) для коммита в `materials/`, либо оригинал размещается на изолированном внешнем томе (`storage_backend = 'local_volume'`) вне Git-индекса, чтобы не раздувать историю и не замедлять `git clone` при старте раннера.

- `git_branch` (`VARCHAR(128)`, default: `'main'`) — рабочая ветка проекта
- `context_data` (`JSONB`, NOT NULL, default: `'{}'`) — цели, входные требования, история ответов фасилитатору
- `schema_version` (`INT`, NOT NULL, default: `1`) — версия для оптимистической блокировки (CAS)
- `created_at`, `updated_at` (`TIMESTAMPTZ`, NOT NULL)

#### 2. Materials (`materials`)
- `id` (`UUID`, Primary Key)
- `project_id` (`UUID`, Foreign Key -> `projects.id`, NOT NULL)
- `filename` (`VARCHAR(255)`, NOT NULL)
- `mime_type` (`VARCHAR(128)`, NOT NULL)
- `size_bytes` (`BIGINT`, NOT NULL, `CHECK (size_bytes > 0)`)
- `storage_backend` (`VARCHAR(32)`, NOT NULL, default: `'git'`): `'git'` (текстовые файлы до 5 МБ) | `'local_volume'` (бинарные файлы вне Git)
- `git_path` (`VARCHAR(512)`, nullable) — относительный путь внутри репозитория проекта (`materials/{filename}`)
- `commit_sha` (`VARCHAR(40)`, nullable) — коммит фиксации материала в Git
- `content_sha256` (`VARCHAR(64)`, NOT NULL) — SHA-256 хеш содержимого файла для дедупликации и проверки целостности
- `created_at` (`TIMESTAMPTZ`, NOT NULL)

#### 3. Runs (`runs`)
- `id` (`UUID`, Primary Key)
- `project_id` (`UUID`, Foreign Key -> `projects.id`, NOT NULL)
- `client_request_id` (`VARCHAR(128)`, NOT NULL, `UNIQUE`) — ключ идемпотентности клиентского запроса на старт запуска (защита от повторного нажатия кнопки «Запустить» и сетевых ретраев, контракт 2.1 и `events v0`)
- `status` (`VARCHAR(32)`, NOT NULL):
  - Активные состояния: `queued` | `running` | `waiting_for_user`
  - Терминальные и пограничные состояния (по словарю спеки 2.5): `partial` | `completed` | `failed` | `cancelled` | `limit_stopped` | `outcome_unknown`
- `current_sequence` (`INT`, NOT NULL, default: `0`)
- `last_artifact_id` (`UUID`, Foreign Key -> `artifacts.id`, nullable)
- `started_at`, `finished_at` (`TIMESTAMPTZ`, nullable)
- `created_at` (`TIMESTAMPTZ`, NOT NULL)
- **Обязательные ограничения и индексы:**
  - `CONSTRAINT runs_client_request_id_key UNIQUE (client_request_id)` — гарантирует идемпотентность старта запуска.
  - Частичный уникальный индекс «один активный запуск на проект» (блокирует запуск параллельного хода из второй вкладки браузера):
    ```sql
    CREATE UNIQUE INDEX idx_runs_one_active_per_project
    ON runs (project_id)
    WHERE status IN ('queued', 'running', 'waiting_for_user');
    ```

#### 4. Operations (`operations`) — журнал идемпотентности записи в Git
Таблица обеспечивает двухфазный протокол записи (`намерение -> коммит -> подтверждение`) и автоматическую сверку при исходе `outcome_unknown`.
- `operation_id` (`UUID`, Primary Key) — детерминированный или сгенерированный раннером ключ операции (также передается в Git commit trailer `Operation-Id: {operation_id}`)
- `project_id` (`UUID`, Foreign Key -> `projects.id`, NOT NULL)
- `run_id` (`UUID`, Foreign Key -> `runs.id`, NOT NULL)
- `kind` (`VARCHAR(32)`, NOT NULL): `'save_artifact'` | `'save_ctf'` | `'save_material'`
- `state` (`VARCHAR(32)`, NOT NULL): `'intent'` (намерение создано в БД до Git-коммита) | `'committed'` (коммит выполнен) | `'confirmed'` (создана запись в `artifacts` и событие `artifact.saved`) | `'failed'`
- `target_git_path` (`VARCHAR(512)`, NOT NULL) — целевой путь внутри репозитория проекта (`runs/{run_id}/result.md`)
- `content_sha256` (`VARCHAR(64)`, NOT NULL) — SHA-256 хеш полезной нагрузки до записи в Git
- `commit_sha` (`VARCHAR(40)`, nullable) — заполняется после успешного коммита или при процедуре сверки
- `created_at`, `updated_at` (`TIMESTAMPTZ`, NOT NULL)

#### 5. Events (`events`)
Синхронизировано с контрактом `events v0` (PR #8): типы событий используют точечную нотацию (`dot.notation`).

- `run_id` (`UUID`, Foreign Key -> `runs.id`, NOT NULL)
- `project_id` (`UUID`, Foreign Key -> `projects.id`, NOT NULL)
- `sequence` (`INT`, NOT NULL) — монотонно возрастающий номер события внутри запуска

- `actor` (`JSONB`, NOT NULL) — роль CoreTeam (`{"roleId": "...", "displayName": "..."}`)
- `payload` (`JSONB`, NOT NULL) — нормализованные данные шага (прогресс, текст, ссылка на `artifactId`, `commitSha`)
- `created_at` (`TIMESTAMPTZ`, NOT NULL)
- **Обязательные ограничения и индексы:**
  - `CONSTRAINT events_run_id_sequence_key UNIQUE (run_id, sequence)` — гарантирует отсутствие дублей и строгий порядок при догрузке/стриминге событий.

#### 6. Artifacts (`artifacts`)
- `id` (`UUID`, Primary Key)
- `project_id` (`UUID`, Foreign Key -> `projects.id`, NOT NULL)
- `run_id` (`UUID`, Foreign Key -> `runs.id`, NOT NULL)
- `operation_id` (`UUID`, Foreign Key -> `operations.operation_id`, NOT NULL)
- `title` (`VARCHAR(255)`, NOT NULL)
- `mime_type` (`VARCHAR(64)`, NOT NULL, default: `'text/markdown'`)
- `git_path` (`VARCHAR(512)`, NOT NULL) — путь внутри репозитория проекта (`runs/{run_id}/result.md`)
- `commit_sha` (`VARCHAR(40)`, NOT NULL) — 40-символьный SHA коммита Git с зафиксированным результатом
- `content_sha256` (`VARCHAR(64)`, NOT NULL) — контрольная сумма SHA-256 содержимого артефакта
- `git_tree_url` (`VARCHAR(512)`, nullable) — URL для просмотра файла/коммита в веб-интерфейсе Git
- `size_bytes` (`BIGINT`, NOT NULL)
- `created_at` (`TIMESTAMPTZ`, NOT NULL)
- **Обязательные ограничения и индексы:**
  - `CONSTRAINT artifacts_run_id_operation_id_key UNIQUE (run_id, operation_id)` — исключает появление второго дублирующего артефакта при повторе после сбоя.

- `commit_sha` (`VARCHAR(40)`, NOT NULL)
- `content_sha256` (`VARCHAR(64)`, NOT NULL)
- `is_internal` (`BOOLEAN`, NOT NULL, default: `true`) — флаг изоляции от публичного API интерфейса
- `created_at` (`TIMESTAMPTZ`, NOT NULL)

### 2.5. Политики записи, сверки `outcome_unknown` и жизненного цикла данных

1. **Confirmed Write (Двухфазная идемпотентная запись `намерение -> коммит -> подтверждение`):**
   - **Шаг 1 (Намерение / Intent):** Перед записью в Git сервис вычисляет `content_sha256` от текста артефакта и создает запись в таблице `operations` со статусом `state = 'intent'`, `operation_id`, `run_id`, `target_git_path = 'runs/{run_id}/result.md'` и `content_sha256`.
   - **Шаг 2 (Физический коммит в Git):** Раннер/воркер записывает файл в репозиторий проекта и делает коммит с трейлерами `Turn-Id: {sequence}` и `Operation-Id: {operation_id}`, получая `commit_sha`.
   - **Шаг 3 (Подтверждение в транзакции БД):** В одной транзакции PostgreSQL обновляется `operations.state = 'confirmed'` (с записью `commit_sha`), вставляется строка в `artifacts` (защищена `UNIQUE(run_id, operation_id)`), добавляется событие `artifact.saved` в `events` и статус `runs.status` переводится в `completed`.
   - Пользовательский статус «Сохранено» не отображается в UI до завершения Шага 3.

2. **Outcome Unknown (`outcome_unknown`) и алгоритм идемпотентной сверки (Reconciliation):**
   - Если после Шага 1 произошел сетевой разрыв, таймаут раннера или падение процесса до завершения Шага 3, запуск переводится в статус `outcome_unknown` (публикуется событие `run.outcome_unknown`).
   - При повторной попытке или фоновом восстановлении воркер **не делает слепой повторный коммит**, а запускает процедуру сверки по незавершенной записи `operations` (`state IN ('intent', 'committed')`):
     1. Воркер проверяет историю коммитов изолированного Git-репозитория проекта по трейлеру `Operation-Id: {operation_id}` и проверяет файл по пути `target_git_path`.
     2. Если коммит найден или файл в HEAD имеет SHA-256, совпадающий с `operations.content_sha256`, повторный `git commit` **не создается**. Воркер берет существующий `commit_sha` и идемпотентно дозавершает Шаг 3 (`INSERT INTO artifacts ... ON CONFLICT (run_id, operation_id) DO NOTHING`, эмиссия `artifact.saved`, перевод запуска в `completed`).
     3. Если коммита в Git нет, воркер безопасно выполняет Шаг 2 и Шаг 3 с тем же `operation_id`.
   - Таким образом гарантируется выполнение критерия 5 спеки 2.3: сбой посреди сохранения никогда не порождает дублирующий коммит или второй артефакт.

3. **Защита от параллельных запусков и конфликтов версий (Concurrency & Version Conflict):**
   - **Идемпотентность кнопки «Запустить»:** Клиент передает `client_request_id` (UUIDv4, сгенерированный на форму запуска). Повторный сетевой запрос с тем же `client_request_id` возвращает уже созданный `run_id` без дублирования.
   - **Блокировка параллельных вкладок:** Частичный уникальный индекс `idx_runs_one_active_per_project` на уровне PostgreSQL гарантирует, что у проекта не может быть двух одновременных запусков в статусах `('queued', 'running', 'waiting_for_user')`. При попытке старта из второй вкладки возвращается `409 Conflict`.
   - **Изоляция Git-блокировок:** Так как у каждого проекта свой собственный Git-репозиторий, коммиты разных пользователей никогда не конкурируют за один `.git/index.lock`.
   - **Оптимистическая блокировка контекста:** При редактировании `projects.context_data` в UI проверяется `WHERE id = :id AND schema_version = :expected_version`.

4. **Recovery (Восстановление сессии клиента):**
   - При перезагрузке страницы клиент запрашивает текущее состояние `runs` и догружает события из таблицы `events` с фильтром `sequence > last_seen_sequence ORDER BY sequence ASC`, после чего подписывается на стрим. Благодаря `UNIQUE(run_id, sequence)` дубликаты и пропуски исключены.

5. **Delete & Retention (Удаление и хранение):**
   - В версии v1 по умолчанию применяется мягкое удаление (`projects.status = 'archived'`).
   - Благодаря модели `repo-per-project`, при поступлении требования на физическое удаление данных конкретного клиента (GDPR / запрос заказчика) его изолированный Git-репозиторий и связанные записи в БД могут быть удалены целиком (`rm -rf` репозитория + каскадное удаление в БД) без переписывания истории других клиентов.

### 2.6. Модель доступов и серверные проверки владения (Server-side ownership checks)

В соответствии со спецификацией доступа эпика 2.5 (`2.5-1-модель-доступов.md`) фиксируются следующие правила авторизации на уровне хранилища, БД и Git:

1. **Границы версии v1 (Организации и совместный доступ):**
   - Организации, команды, мультиарендность (multi-tenancy) и совместное редактирование проектов (sharing/RBAC) **вынесены за границы версии v1**.
   - Доступ строится на строгой модели единого владельца: один проект принадлежит ровно одному `owner_id` (привязка к сессии пользователя в Better Auth).

2. **Физическая и логическая изоляция проектов:**
   - **Изоляция на уровне Git (выполнение критерия 8 спеки 2.3 и HADI-T3):** Поскольку каждый проект хранится в отдельном Git-репозитории, раннер 2.4 при выполнении запуска монтирует том только одного конкретного репозитория проекта. Даже при компрометации процесса раннера или выдаче проверяющему доступа к репозиторию проекта доступ к материалам и отчетам чужих проектов физически невозможен.
   - **Поэкземплярная серверная валидация в БД:** Передача `projectId`, `runId`, `materialId` или `artifactId` от клиента не подтверждает права доступа. Каждый запрос проверяет `project.owner_id == session.user_id`:
     ```sql
     SELECT a.* FROM artifacts a
     JOIN projects p ON a.project_id = p.id
     WHERE a.id = :artifact_id AND p.owner_id = :current_user_id;
     ```
   - При отсутствии совпадения сервер возвращает безопасный статус `404 Not Found` (или нейтральный `403 Forbidden` без раскрытия факта существования чужого проекта).

3. **Права ролей и сервисные ключи:**
   - **Гость (Guest):** Доступны только публичные демо-материалы; создание проектов, загрузка файлов и запуски заблокированы.
   - **Пользователь (User):** Полный доступ (чтение/запись/запуск) только в рамках своих проектов.
   - **Администратор (Admin):** Отдельная служебная сессия без автоматического сквозного доступа к клиентским проектам. Любое служебное обращение фиксируется в неизменяемом аудит-логе.
   - **Ключи доступа (API Keys / Service Tokens):** Изолированы во внутреннем контуре бэкенда/раннера и никогда не транслируются в публичные события и интерфейс.

## 3. Последствия (Consequences)

### Положительные:
- **Полная изоляция данных клиентов (HADI-T3 и критерий 8 спеки 2.3):** Модель «один репозиторий на проект» исключает утечку соседних проектов при монтировании тома в раннер 2.4, устраняет глобальную блокировку коммитов между проектами и позволяет физически удалять данные одного проекта без переписывания чужой Git-истории.
- **Идемпотентность и отсутствие дублей при сбоях:** За счет `runs.client_request_id UNIQUE`, частичного индекса на активный запуск, таблицы `operations` и `UNIQUE(run_id, operation_id)` в `artifacts` сетевые ретраи и падения процесса не создают ни параллельных запусков, ни дублирующих коммитов.
- **Сквозная совместимость контрактов:** Единый словарь статусов (`waiting_for_user`, `limit_stopped`, `outcome_unknown`) и событий (`artifact.saved`, `role.started`) исключает ошибки маппинга между командами 2.1, 2.3, 2.4 и 2.5.
- **Прозрачный аудит:** Каждая версия отчета привязана к неизменяемому `commit_sha` и `content_sha256`.

### Ограничения и риски:
- **Управление множеством Git-репозиториев:** Вместо одного репозитория инфраструктурный слой должен автоматически инициализировать bare/working репозиторий при создании проекта и управлять квотами дискового пространства.
- **Непригодность Git для тяжелых бинарных файлов:** Хранение больших PDF и датасетов в Git запрещено квотой (до 5 МБ на текстовый файл); для тяжелых вложений требуется либо передача извлеченного текста, либо хранение бинарного оригинала на внешнем томе / в S3.

## 4. Рассмотренные альтернативы (Considered Alternatives)

В соответствии со спецификацией 2.3 (п. 2, 6) и DoD документации рассмотрены четыре архитектурные альтернативы:

| Альтернатива | Описание подхода | Плюсы | Минусы и причина отказа (или выбора) | Статус |
| :--- | :--- | :--- | :--- | :--- |
| **1. Единый монорепозиторий Git на все проекты (`repo-root/projects/{id}`)** | Все проекты всех пользователей хранятся в разных папках одного общего Git-репозитория. | Простота инициализации (один репозиторий при старте системы). | **Отклонено:** Нарушает критерий 8 спеки 2.3 и HADI-T3 (любой клон/монтирование в раннер открывает доступ ко всем проектам); все коммиты всех клиентов упираются в одну блокировку `.git/index.lock`; невозможно удалить данные одного клиента без `git filter-repo` всей истории. | Отклонено |
| **2. PostgreSQL + Объектное хранилище (S3 / MinIO)** | Метаданные и события в PostgreSQL, а материалы и сгенерированные Markdown-артефакты — в S3-бакете с версионированием объектов. | Нативная работа с тяжелыми PDF и бинарными датасетами любого размера; отсутствие накладных расходов на `git clone`. | **Отклонено для артефактов v1 (оставлено как расширение для больших бинарников):** Противоречит базовому требованию заказчика иметь полноценную Git-историю коммитов (`git log`, `git diff`, трейлеры `Turn-Id`) и возможность просматривать сгенерированные отчеты и `.ctf`-манифесты напрямую через интерфейс Git. | Отклонено для отчетов v1 |
| **3. Только PostgreSQL (хранение текстов отчетов и файлов в `TEXT`/`BYTEA`)** | Полный отказ от файлового/Git-контура; хранение всех версий отчетов, манифестов и файлов в таблицах БД. | Атомарные ACID-транзакции без двухфазной сверки между БД и файловой системой. | **Отклонено:** Раннер 2.4 работает с файловым рабочим деревом и фиксирует промежуточные ходы через Git (`Turn-Id`); раздувание таблиц PostgreSQL и WAL-логов от `BYTEA`/версий документов; отсутствие нативного `git diff`. | Отклонено |
| **4. PostgreSQL + Изолированный Git-репозиторий на проект (`Repo-per-Project`)** | Метаданные, события и журнал идемпотентности в PostgreSQL; у каждого проекта свой изолированный Git-репозиторий с лимитом на размер файлов. | Полная изоляция тенантов и раннера 2.4; отсутствие конкуренции за lock между проектами; легкое удаление отдельного проекта; выполнение требования заказчика по Git. | Требует протокола двухфазной сверки (`operations`) и ограничения на размер бинарных материалов. | **Принято (целевое решение)** |

## 5. Открытые вопросы заказчику (Open Questions to Customer)

Для прохождения контрольной точки **7.10** и закрытия требований спецификации 2.3 (п. 6, 7) на согласование заказчику выносятся следующие вопросы:

1. **Формальное подтверждение источника требования «Git вместо S3» и квоты на `materials/`:**
   - *Контекст:* Хранение тяжелых PDF и датасетов (по 10–50 МБ) непосредственно в Git необратимо раздувает историю репозитория и замедляет старт раннера.
   - *Вопрос:* Подтверждаем ли мы для v1 жесткий лимит **до 5 МБ на файл (только текстовые форматы `.md`, `.txt`, `.json`, `.yaml`, `.csv`)** для коммита в Git-репозиторий проекта, а для бинарных файлов (PDF, архивы, датасеты) — хранение вне Git (на выделенном томе/S3 с фиксацией только `content_sha256` и текстовой выжимки в Git)? Просьба зафиксировать ссылку на номер протокола встречи в шапке ТЗ.
2. **Политика хранения (Retention Policy) и физическое удаление (Hard Delete):**
   - *Контекст:* В v1 заложено мягкое удаление (`status = 'archived'`) и бессрочное хранение для демонстрационного контура.
   - *Вопрос:* Каков требуемый срок хранения (`retention period`) архивных проектов, истории `events` и Git-репозиториев в промышленном контуре (например, 90 / 180 / 365 дней после архивации) и требуется ли функция немедленного физического уничтожения репозитория проекта по запросу пользователя?
3. **Персональные данные (ПДн / 152-ФЗ) и очистка истории Git:**
   - *Контекст:* Пользователи могут загрузить в `materials/` или ввести в диалог с фасилитатором персональные данные или коммерческую тайну, которые попадут в коммиты и `events.payload`.
   - *Вопрос:* Допускается ли обработка ПДн в контуре v1, требуется ли автоматическое маскирование (PII scrubbing) перед записью в Git/БД и каков регламент реагирования при обнаружении секретов/ПДн в истории коммитов?
4. **Регламент резервного копирования и восстановления (Backup & Disaster Recovery — RPO / RTO):**
   - *Контекст:* Гибридная схема требует консистентного бэкапа PostgreSQL и файловых томов с Git-репозиториями проектов.
   - *Вопрос:* Какие целевые показатели RPO (допустимая потеря данных по времени, например <= 1 часа) и RTO (время восстановления сервиса) требуются заказчику, и куда должны выгружаться снапшоты Git-томов и дампы PostgreSQL?
